# Batch 1: the pilot does not show the saving

12 November 2026. 90 runs of `claude-haiku-5-5` on the order desk in `../../program/`, footprintjs 12.1.0 and foottrace 1.14.0, harness at commit `7854194f`, caching off. Spend at the rule's prices: 0.4574 dollars.

Everything of the batch is in this folder as the harness wrote it: `order.json` (the plan and its seed), `started.jsonl`, `runs.jsonl`, the generated `report.md`, and one transcript per run under `transcripts/`. Nothing was run again and nothing was edited.

## The decision, by the rule written before the run

`report.md`, generated by `harness/report.mjs`:

> Stop and look: on the seven data-flow faults set-up 3 solved 20 of 21 (95%) of its finished runs against set-up 1's 21 of 21 (100%) (7.3% more tokens per solved task); it solved a smaller share.

| Faults | Set-up 1: code and logs | Set-up 2: plus the map | Set-up 3: plus the record tools |
|---|---|---|---|
| Seven data-flow, solved | 21 of 21 | 21 of 21 | 20 of 21 |
| Seven data-flow, tokens per solved task | 38,081 | 34,774 | 40,853 |
| Three controls, tokens per solved task | 57,838 | 69,007 | 45,507 |
| All ten, solved | 30 of 30 | 30 of 30 | 29 of 30 |
| All ten, tokens per solved task | 44,008 | 45,044 | 42,298 |

No robustness row of the rule holds (`report.md`, "Does the result hang on one fault or one run?"). The claim under test, that the map and the run record cut the tokens an agent needs to fix a fault, is not shown by this batch.

## The independent reading

A reader who had not built the harness read the batch before any number was quoted. Its scripts and their outputs are in `review/`; each reads the transcripts directly and imports nothing of the harness (`python3 -I review/<script>.py <this folder> <bench/agent-debug>`).

- **Not void.** No tool answer in any of the 90 transcripts holds anything the working folder does not hold: 0 hits for 55 strings that must never appear (fault ids and descriptions, hidden fixture names and expected values), and every `read_file`, `list_files` and `search` answer is content of the working copy at that point of the run (`review/check_reads.out`). The record tools printed the faulty run, never a value of the correct program (`review/record_vs_run.out`).
- **The baseline was not hobbled.** One system text for all 90 runs, one definition per shared tool, no error and no cut answer in set-up 1 (`review/starts.out`, `review/numbers.out`).
- **The numbers are the batch's.** 13 fields per row compared between the transcripts and `runs.jsonl`: 0 differences. The headline, the robustness rows and the spend recomputed from the transcripts equal `report.md` (`review/numbers.out`).
- **One wrong cell in `report.md`.** "Named the faulty step" counts `setup3-wrong-mapper-key-r1`, whose summary names another step and contains the word "tax" in "excluding tax and shipping". The column should read 20, not 21, for set-up 3 on the data-flow faults. `harness/score.mjs · namesStep` matches a step's id as a word anywhere in the summary, which is fragile for ids that are common words. The header of `report.md` also says rule version 1.4; the rule is 1.5, which changed only what the smoke batch must show.

## What three runs per cell can carry

Per repeat, the data-flow headline of set-up 3 was 45,619, 40,683 and 36,938 tokens per solved task; set-up 1's was 38,518, 36,853 and 38,872 (`review/job4.out`). The gap between the set-ups (2,772) is smaller than set-up 3's own spread between repeats (8,681), and in the third repeat the sign flips. Each sub-result rests on one fault: without `wrong-mapper-key` set-up 3 is 9.3% cheaper on the data-flow faults; without `wrong-default-branch` it is 3.8% dearer on the decision faults; without `wrong-constant` it is 26.7% dearer on the controls.

A careful reader may say:

- On this one program and this one model, with no caching, the record tools did not reduce tokens per solved task on the seven data-flow faults: 40,853 against 38,081, and one unsolved run against none.
- Three runs per cell cannot tell a difference of this size from noise.

A careful reader may not say that the tools save or cost tokens in general, that the advantage on the decision faults or on the controls is real, or that anything here is significant.

## Why, from the transcripts

1. **The plain agent solves everything.** Set-up 1 solved 30 of 30 in 5.83 requests per run, reading 11.8 files per run of the 35 under `src/`. Every fault here can be found by reading a step's code against the comment above it, and no run in any set-up added a log line (`review/checks.out`). The solve rate has no room left.
2. **The record tools cut what is read, not the number of requests.** Set-up 3 made 4.4 `read_file` calls per run against 11.8, and 5.77 requests against 5.83. With caching off every request pays for the whole conversation again.
3. **The tools' own definitions cost more than the gap.** Set-up 3's first request is 2,554 input tokens against 1,665: 889 more on every request, 13.1% of its data-flow tokens. Without them it would stand at 35,482 against 38,087 (`review/extra.out`). That is still far from the 25% the rule asks for.
4. **The tools do not say where a step's code is** unless `step` is asked. In 15 of 30 set-up 3 runs a request went only to `step`, `search` or `list_files` before the faulty file was read; in set-ups 1 and 2, none. Set-up 3 first read the faulty file at request 3.55, set-up 1 at 2.90 (`review/extra.out`).
5. **A true answer in the wrong order.** On the sub-flowchart fault (`wrong-mapper-key`) `why` printed the cause (`tax#12 … read billingRegion`, where the tax is for the region the order ships to), and it was the same true text in all three runs. It stood at link 10 of 19, depth 5 of 6, in a 26-line answer that lists the nearest steps first. All three runs went to a nearer step first. One changed that step: the key named in the task came out right, the eight visible tests passed, and four fixtures were wrong, the task's own among them. The other two found the mapper by reading files.
6. **The record helped when its first answer named the right step** (`wrong-default-branch`: 40,131 against 65,955; `wrong-constant`: 47,141 against 102,982; `missing-write`, cheaper in every run) and cost more when it did not, or when the plain agent found the fault in four requests anyway (`swapped-key-in-fork`: 26,673 against 16,358).

Paid with caching, the picture would move toward set-up 3 but the data cannot say how far: per solved data-flow task it sent 9,746 new tokens against 10,370 and re-sent 31,107 against 27,711 (`review/numbers.out`). No price is assumed here.

## What this batch did not test

The rule's own list stands (`../../RULE.md`, "What this pilot does not measure"): one small program written by the people who make the library, one model, no caching, three runs per cell. Two things the transcripts add: the program is small enough to find any of these faults by reading, and each fault contradicts a comment beside it, so no run needed to know what a run actually did. Whether the record pays for itself on a program too large to read, or on a question about one run that no code comment answers, is not a result of this batch in either direction.

## What follows

By the rule, nothing is built on this result. A further batch is a new experiment with its own rule written first, in its own folder. The two faults of the harness named above are to be fixed before it.
